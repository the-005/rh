# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A photography portfolio website built as a 3D infinite pannable space. Uses React 19 + React Compiler, Three.js, React Three Fiber, TypeScript, and Vite.

## Git workflow

After every meaningful change: stage specific files, commit with a clear message, and push to `origin main`.

```bash
git add <files>
git commit -m "concise description of what and why"
git push origin main
```

## Tickets

The owner tracks the work on a Notion board: the **Projects** database on the `rh` page (`collection://3dca5953-9846-8098-b2dc-000b94ef2427`), reached through the Notion MCP server. Keep it current as part of the git workflow:

- **Starting work on a ticket:** set it to **In progress**. It stays there while the owner looks at the work too; there's deliberately no status for the owner reviewing it.
- **Client review** (in the board's "in progress" group) means finished from our side and waiting on Ruben's approval. Move a ticket there only when the owner says it's ready for him. Feedback with changes moves it back to In progress (the Changes record keeps each round); approval means Done, which only the owner sets. **"Talk about it" is not Client review:** a ticket that only needs Ruben's input (like the navigation placeholder) stays In progress and is linked to the meeting instead, through the meeting's Tickets property and its agenda.
- **Every pushed commit goes in its ticket's record.** A ticket page is three sections: **About project** (what it is), **Action items** (open to-dos only), then **Changes**, the record of every revision. Add each commit at the **top** of Changes, newest first, as a bullet: the short hash linked to `https://github.com/the-005/rh/commit/<hash>` in code style, then a short, clear line on what changed. No dates. Insert by replacing the `### Changes` heading with itself plus the new bullet. The record exists because changes get revised and reversed often; log reversals too, and don't edit or delete old entries.
- **Every visible change gets a screenshot under its bullet.** The site only ever shows the latest version, so this is how ideas we've since overwritten can still be shown to the client. Shoot it before the next change overwrites it: headless Chrome (playwright with `channel: "chrome"`) at 1440×900 against the dev server, in the state the change is about (a row hovered, idle, playing…), one shot per state when there are several. Save as JPEG at quality 85 (`sips -s format jpeg -s formatOptions 85`), upload with Notion's file upload, and nest it under the bullet with a short caption: a tab-indented `<image src="file-upload://…">caption</image>` line in the same edit that adds the bullet. **Motion gets a clip too** (transitions, playback, idle fades): playwright `recordVideo` at 1440×900, with a visible cursor dot added only for the recording (headless has none), then ffmpeg to H.264 MP4 (`-vf crop=1440:812:0:0`, since headless recordings carry a grey strip at the bottom, `-crf 26 -movflags +faststart -an`). The owner is on Notion's free plan, so each upload must stay **under 5 MB**; a 15s clip comes to about 0.4 MB.
- **A new request, or a loose end we leave open:** a new **Backlog** ticket from the database's template (it has the three sections). Titles are short and lowercase, like the rest of the board. Set Page and Scale; leave Priority to the owner.
- **The tuning table** (`collection://dd6292d7-c17f-4b38-ba0d-daba5f3afebd`, on the `rh` page) lists every timing, easing, colour, size and threshold the motion depends on, one row per value, with the constant or CSS rule to edit. Sorted by Step it reads as each page's timeline. When a commit changes one of these, update its row in the same pass, and add rows for new ones. The index and project pages are in; add other pages as we work on them.
- **Never set Done.** The owner does, or says to.

## Hosting

**Staging is on Netlify, deploying from GitHub**: every push to `main` rebuilds and redeploys, so the owner's friend can follow progress. `netlify.toml` holds the build (`npm run build` → `dist`, `NODE_VERSION` 22) and the single-page-app catch-all (`/*` → `/index.html`, status 200), without which a reload on `/index` or `/project/:id` 404s. `/index` also needs its own forced rewrite ahead of the catch-all: Netlify otherwise reads it as the address of `index.html` and 301s it to `/`, so the index link opened the gallery. **`vite.config.ts` must keep `base: "/"`**: the Codrops template shipped `"./"`, which makes built asset URLs relative, so a direct load of `/project/PR-02_HE` asked for `/project/assets/…js`, got index.html back, and rendered blank. The tab title is `rh wip` and the favicon a plain black square (`public/favicon.svg` + `favicon.png`).

The splash plays `public/splash.mp4`: H.264 CRF 28, no audio, faststart, 9.4MB. It's visually matched against the owner's 30MB edit `public/PR-01_DE_58.mp4`, which stays **uncommitted** (the 448MB master is in the client folder). CRF 32 (3.7MB) smoothed away the faint point-cloud sparkle.

## Media

The site has two sets of images. **Work** is what the canvas (gallery), the project pages and the index show; they share `src/work/manifest.json`. **Research** is the outlier: its own page and its own `src/research/manifest.json`. Say "Work" for the first set. "Project" means a single one.

Both scripts encode through `scripts/media.ts`, which follows the owner's manual Squoosh process so a scripted batch matches a hand-made one. Treat these settings as fixed; change them only when asked:

- **JPEG through MozJPEG (Squoosh's JPEG encoder), quality 85**, progressive.
- **Longest side 3000px, never enlarged.** It's a photography site, so keep the most resolution the cap allows; don't lower it to save bytes.
- Turned upright from the camera's rotation tag, converted to sRGB from any embedded profile, metadata stripped — as Squoosh does.
- **Order comes from the name**, natural sort (`_2` before `_10`). Don't reorder by hand; rename the source.
- Images only. Videos have no process yet.

Originals are never written. Copies newer than their source are skipped (`--force` redoes them).

**Work** — `npm run work:images -- "<client folder>"`. The client folder holds one folder per project. **The folder name is the project's title, used as-is** (`PR-02_HE`), and also its `/project/:id`. Images sit in subfolders (`PR-02_IMG`, `PR-01_IMAGES`) or loose; subfolders with `VID` in the name are skipped. Each image gets two copies: `public/work/<project>/<name>.jpg` at 3000px for the project page and index, and `public/work/<project>/canvas/<name>.jpg` at **1000px for the canvas**, which holds every texture on the GPU at once (3000px would be about 8GB for 245 images). The client folder is the source of truth: anything in `public/work/` it no longer accounts for is deleted, and `src/work/manifest.json` — `{ url, canvasUrl, width, height, project }[]` — is rebuilt every run. The client folder today is `~/Downloads/[optimize + format]`: 11 projects, PR-01_DE … PR-012_PV (no PR-10), 245 images.

**Research** — `npm run research:images -- "<source folder>"` writes `public/research/<name>.jpg`, then rebuilds `src/research/manifest.json` — `{ url, width, height }[]` — from everything in `public/research/`. Run it once per source folder. Its images are placeholders (PR-01_DE, which is also a Work project).

In the client's folders, images and videos mostly share one number sequence per project: the gaps in the image numbers are videos. Not every file follows it; PR-01 has `_64`/`_65` as both a JPEG and an MP4, some videos have unnumbered names (`DFC_P20_04.mp4`), and PR-04_FC's images aren't numbered at all (`FASHIONCLASH COVER.jpg`, `FC24_01.jpg` … `spatial 02.jpg`), so they sort by name.

## Architecture

### Data flow
`src/work/manifest.json` → `App` → `InfiniteCanvas` → Three.js scene

Media items are `{ url, canvasUrl, width, height, project }`. Images live in `public/work/`; the canvas loads `canvasUrl` (1000px), everything else loads `url` (3000px), except that the project page starts most images on their `canvasUrl` and upgrades them (see `src/project/`). Items with a matching `project` field are grouped into a project page accessible by clicking the image. There is no category split (the old art/commerce filter is gone).

### Key modules

**`src/infinite-canvas/`** — the core 3D engine:
- `scene.tsx` — four components: `InfiniteCanvasScene` (Canvas setup, fog, DPR, tuning panel UI), `SceneController` (input + chunk management), `Chunk` (spatial cell + debug labels), `MediaPlane` (single image plane with depth cycling + fade). Also contains `ChunkLabel` (debug wireframe + coord sprite).
- `constants.ts` — physics/render constants. `CHUNK_OFFSETS` defines the 3D grid of visible chunks (currently dz = −1..1, dx/dy = −3..3).
- `tuning.ts` — mutable singleton `tuning` object read live by `useFrame` and `generateChunkPlanes`. Sliders in the tuning panel write directly to this object; changes take effect without remounting except for generation params (density, size, cycle length, Z spacing) which call `bumpGen()` to clear the plane cache and increment `tuningGenVersion`.
- `texture-manager.ts` — texture loading/caching, from each item's `canvasUrl` (the 1000px copy).
- `utils.ts` — `generateChunkPlanes` (seeded RNG, QMC depth phases, staggered-lattice XY placement), LRU plane cache (max 256 entries), chunk update throttle logic.

**`src/app/index.tsx`** — root `App`; wires manifest → `InfiniteCanvas` + `SplashVideo` + `Frame`. There is no loading overlay or progress bar (removed at the owner's request); planes simply fade in as their textures arrive.

**`src/project/`** — project page + canvas↔page transition. This is the owner's priority surface. Every rule below was asked for; the reasons are given so they don't get undone.

- `index.tsx` — `ProjectPage`, on white, over the canvas. Phases `arrive | strip | leaving`. **Since 2026-10-03 the page is a full-height strip** (the owner's idea, tried first in the Strip Flip artifact): the clicked image scaling up into a looping row, with click halves and a one-swipe-one-image wheel, is gone (in git history before this change).
  - **Layout.** At arrival, one row at equal height, fit-to-width (32px `MARGIN`, 4px `GAP`, row height capped at 50vh), vertically centred. Everything moves by `transform` on `.slot` wrappers. Each `.slot` is `overflow: hidden`, so an image rising into the row is masked at the row line and never shows below it.
  - **Arrival (part 1).** The project's images are rotated so the clicked one leads (slot 0, at the left margin): **the clicked image is always the first**. The canvas plane flies into that slot (1000ms expo-out); only once it is pinned at rest is the DOM `<img>` revealed (`decode()` first, two frames of overlap) and the plane hidden, so the handoff can't be seen. Then the other images rise 32px into place in a wave, left to right: **50ms apart (`RISE_GAP_MS`), squeezed evenly into 1.5s (`RISE_WAVE_MAX_MS`) when that would run longer** (`riseDelays`). That's the owner's "capped" pick from the stagger study in the Strip Flip bench (4 Oct); only PR-01 (52 rising, 29ms apart) and PR-08 (48ms) are capped, and the strip is ready 2.56s plus the wave after the click, 2.8–4.1s. It was 70ms apart with no cap (PR-01's wave took 3.6s).
  - **Direct link** (`/project/:id` typed, reloaded or shared; no plane to fly in), the owner's spec: **an empty white page until every image in the row has loaded, then the arrival plays**: the whole row rises in the same wave, the first image leading, and the zoom follows as usual (`arriving` state; the zoom counts from the start of the wave). The page is opaque white from its first frame, and the canvas is paused from the start, since it never shows. If the row hasn't loaded after `ROW_LOAD_MAX_MS` (8s) it plays anyway, and late images appear as they arrive. It used to fade in from transparent over the canvas, 0.3s after mount, so the black page ground showed through first (the "black flash on direct load" ticket, 4 Oct; not the splash, which never mounts on a deep link).
  - **Zoom (part 2).** After `FUSE_PAUSE_MS`, the **whole row scales up** to `STRIP_HEIGHT_FRAC` (**100%** of viewport height, the owner's first try) over 600ms on `cubic-bezier(0.42, 0, 0.58, 1)`, the clicked image ending **at the left edge** (x = 0, no margin). **The gaps stay 4px** (the owner asked): each slot translates and scales on its own, which keeps every gap at `GAP` all the way through and still reads as one zoom. A uniform scale would have made them 43px for PR-02 and 212px for PR-01. **The strip is laid out at its final size from the start** (after wakawaka.world's intro, which lays its page out full size and only pushes it back in depth): at arrival each slot is shrunk into the row by its own `scale(rowH ÷ stripH)`, and the zoom only takes that away, so nothing is ever blown up from a small layout and nothing re-lays out when it ends. The first version did the opposite (slots laid out at row size, scaled up 4–53×, then re-laid out at full size) and the owner saw it flicker as it grew and then snap into place. **The zoom runs from script, not as a CSS transition** (rAF over `zoomEase`, the same `cubic-bezier(0.42, 0, 0.58, 1)`), and slots have no `will-change`. A transition hands each image to the compositor as its own layer, drawn once and resized every frame: on PR-01 (53 images, point-cloud renders full of fine specks) consecutive frames alternated between soft and sharp drawings and the end jumped to a fresh one, the flicker the owner saw only there, and 53 full-size layers is more than the GPU keeps. From script, the strip is redrawn at its real size each frame and the last frame is the resting one. React's transform for the slots switches from row to strip only on `settled`, after the script is done. The exit still promotes the on-screen images it moves. The rise is `RISE_PX ÷ shrink` in a slot's own units, so it still reads 32px. **The images that get big in the zoom are decoded before it** (`growsLarge`: taller than `PREDECODE_ABOVE`, a quarter of the strip, at their peak, which is full size if they end on screen or their size as they leave the window; 6–8 per project). Their decode starts when the page opens and the zoom waits for it, as wakawaka waits on its hero images, for at most `DECODE_WAIT_MS` (1s). Left to the zoom, the browser decoded them mid-zoom, larger each time as they grew (33 decodes on PR-01), and a first visit dropped frames where a second (cached) didn't. Only those: decoding every image at full size up front was about 1GB on PR-01. **Headless Chrome here renders on the real GPU** (Apple M4 Max, Metal), so recordings show what the owner sees; comparing consecutive frames (`ffmpeg` at 30fps) is how the PR-01 flicker was found.
  - **Scroll (part 3): free and continuous, with momentum.** No loop: the strip ends when its last image reaches the right edge (`maxScroll`). Wheel (either axis, so a mouse wheel works), trackpad, arrow keys (`KEY_STEP_FRAC`, half a window) and **click-and-drag** (mouse, pen or touch; `grab`/`grabbing` cursor) move a target, and `.row` eases toward it in a rAF loop (`SCROLL_EASE` 0.1 of the distance per 60fps frame), so a mouse wheel's steps become a glide and a trackpad keeps its own momentum. A drag let go while moving flings on for `FLING_MS` (250ms) at its release speed, unless it was held still for `FLING_STALE_MS` first. The scroll lives in refs and the row's inline transform, outside React. `busy` freezes input during any move (the canvas half is `isCanvasFrozen`). `preventDefault` on wheel and `touch-action: none` keep the page and browser-back out of it. The wheel and fling values are tuned on simulated input only; the owner's trackpad is the real test.
  - **Current image** (the owner's rules): **at the start of the strip, always the first image** (the one you clicked), and **at the end, always the last**, whatever else is showing (within `END_SLOP_PX`, 1px). In between, **the one taking up most of the screen**; when two are within a pixel, the one over the centre (`imageAt`). It drives the counter and is the image that goes home on exit, so closing before you scroll leaves with the image you clicked, and closing at the end leaves with the last one.
  - **Counter.** `01 / 33`, **counted from the clicked image** (the strip's own order, so it never jumps from the last number back to 01). Centred in the top row level with the wordmark, shown only in `strip`. The counter and × are white with `mix-blend-mode: difference`, like the frame, because at full height they sit on the pictures.
  - **Cursor.** `grab` on the whole overlay, `grabbing` while dragging (`.dragging`). One cursor throughout, so it never flicks between moves; clicks don't navigate any more.
  - **Exit, from any image** (× or Escape). Decided by the owner: "the user can exit from any image, we will just change the image on the homepage that they come from to the image that they closed out with." One move, straight back into the canvas (the owner didn't want a scale-down to the row first, or a plain fade), and **only the image you're on goes**:
    1. `swapTransitionSource` puts the current image on the plane the project was opened from. Once the plane is drawing it (texture loaded and bound), it re-pins over the image and flies home (1000ms expo-out), becoming exactly the size and brightness that spot has on the canvas. `setCameraGoal` eases the camera onto the spot so it lands centred, **already at the mouse-parallax tilt the cursor asks for** (`PARALLAX_AMOUNT`, the drift eases to it while the base makes up the difference), so nothing moves after the landing. It used to unwind the tilt to zero; at the landing the parallax then caught up to the cursor, which is usually up on the × (the biggest tilt), sliding the gallery and the landed image off-centre (the owner's pick of three ideas, 4 Oct). The spot keeps the new image until its next depth cycle. **The rest of the canvas fades back in during the flight, `CANVAS_RETURN_MS` (300ms) in** (`returnCanvas`), not at the landing; input stays frozen until it lands. The owner saw the image sit alone on white for most of the flight (it has shrunk by ~150ms) and asked for the gallery sooner (4 Oct). At 300ms the camera's centring pan is mostly done, so the gallery fades up in place around the image; at 0ms it came up sooner but visibly slid as the camera centred (both clips on the ticket).
    2. **The rest of the strip vanishes the moment you close** (opacity 0, no transition): the owner's "gone at once" pick from the exit study in the Strip Flip bench (4 Oct). Until then the strip shrank with the plane as one piece (0e1295a), hugging its on-screen rect every frame; the plane still publishes that rect (`setHeroScreenRect`), but the page no longer reads it. The bench keeps the other options (shrink with it, scatter, shrink then scatter, shrink more and scatter all) for comparison.
    - Falls back to a plain fade if the texture doesn't arrive within `SWAP_TIMEOUT_MS` (1.2s), and on Escape mid-move. (Deep links to `/project/:id` have no plane either and fade out.)
    - **Known and intended:** "home size" is the spot's real size at its depth, so a spot that was close to the camera **grows** on the way out and a far one shrinks a lot; a spot that was faint when clicked arrives faint (at full height this shows more: a faint spot can all but vanish, and since only that image goes home now, nothing else is left on screen when it does). The shrink is front-loaded: expo-out plus perspective puts most of it in the first ~150ms.
  - **Most images start as their 1000px canvas copy** (the owner's idea, option "a"). Only the images that get taller during the zoom than their `canvasUrl` copy can show sharply start at full size (`startsFull`: peak share × strip height × `devicePixelRatio` > the copy's pixel height, `CANVAS_COPY_PX` 1000 on the long side; 2–4 per project). The rest start on the copy, often already cached from the canvas, and **after the zoom are upgraded to full size in strip order**, `UPGRADE_CONCURRENCY` (2) at a time: each loads and decodes in a detached `Image` first, then swaps in (`upgraded` state), so it only turns sharper, with no flash (checked frame by frame on a throttled connection with the swap on screen). Opening PR-01 went from about 31MB of downloads to about 5MB before the zoom (3 full-size images, 1.9MB, plus the copies, 3.6MB); the remaining full-size files follow in the background.
  - **The canvas stops rendering while the page covers it** (`setCanvasPaused` in `transition-origin.ts`, applied through the Canvas `frameloop` prop, because R3F re-applies that prop on every re-render). Paused once the arrival handoff is done (or the direct-link fade-in), resumed at the start of the exit and by `releaseTransition`. On a first visit its loop and texture decodes cost the zoom a ~115ms freeze. With both fixes a cold first visit zooms at a steady 60fps (measured: rAF intervals over the zoom, and a Chrome trace for what ran during it).
  - The canvas-size copy of the current image is warmed whenever it changes, so the swap on exit is usually immediate.
  - **Video in the strip** is open: the owner's question is what happens when a video half on screen is played. Deferred.
- `transition-origin.ts` — module-level store coordinating the canvas↔page handoff (modeled on Codrops "persistent page transitions"). The clicked plane (addressed by **registry key**, not URL, since one image can sit on several planes) flies in `MediaPlane.useFrame` (`getHeroTween(regKey)` branch in `scene.tsx`). `beginHeroTween(mode)`: `"in"` flies canvas → a measured DOM rect; `"out"` re-pins to a DOM rect and flies home, taking its aspect from that rect because the image may have changed. `cycleX`/`cycleY`/`absoluteZOffset` stop updating once that branch takes over, so they still hold the plane's canvas spot (that is "home"). Other planes dim, and canvas input freezes, while `active`; on the way home `returnCanvas()` lets the others fade back in before the landing (`isCanvasDimmed` covers the splash frame too). Also: the per-plane **media override** (`swapTransitionSource` / `getMediaOverride` / `takeSwapWaiter`, pinned to the depth cycle it was first read in) and the homeward plane's **screen rect** (`setHeroScreenRect` / `getHeroScreenRect`). `releaseTransition()` (close/unmount) un-hides, un-dims, un-freezes and clears the waiter and rect, but deliberately not the overrides. `holdTransition()` re-asserts the hold because StrictMode's double-invoked mount runs a release in between. The entry effect must only ever restore inline styles to `""` (the class value); capturing "original" inline values breaks under StrictMode re-runs.

**`src/frame/index.tsx`** — HTML overlay header. The top row carries a `Home` wordmark at the left — a placeholder for the logo, and the way back to the canvas — **Gallery and Index centred on the page** (`.frame__centre`, absolutely centred; the two views of the same work) and Research and About at the right. Both inherit the frame's `mix-blend-mode: difference`, so they read white over the canvas and black over the index, about and project pages. The nav is hidden while a project is open (`showNav`).

**`src/about/index.tsx`** — `AboutPage`: the third view, at `/about`, on the same white as the index, at `z-index: 100` under the frame. **Currently empty**: all placeholder copy (statement, contact, studio, services, clients) was removed at the owner's request, pending real text. The old two-column layout is in git history (before this change).

**`src/research/index.tsx`** — `ResearchPage`: the Research images as a grid, at `/research`, on the same white as the index and about. Started as the Codrops grid-layout-transition demo (MIT), with its numbering and GSAP FLIP tween removed and its scale buttons replaced by a slider (50–150%, centred one line under the frame's Gallery/Index links, which took the top row's centre). The slider sets a target tile width (`BASE_TILE` 150px × scale). The grid is `repeat(auto-fill, minmax(--tile, 1fr))`, so it fits as many columns as the row holds, stretches them to fill it, and moves a column at a time with both edges fixed. Each change lands in a single frame, the way Eagle's zoom does (checked frame by frame against a recording); tweening tiles between cells read as lag. **Stops** at 50/75/100/125/150 **snap on release**: a drag moves freely, and letting go within `SNAP` (6) of a stop lands on it. Anything further out stays where it was released; `SNAP` 12.5 would make every release snap. Arrow keys never snap, or 101 would snap back to 100 and the thumb would stick. No value readout. Images keep their own aspect ratios and **hang from the top of each row** (`align-items: start`), not centred. Phones get 3 fixed columns and no slider. It reads `src/research/manifest.json` (see Media).

**`src/projects/index.ts`** — the Work manifest grouped into one entry per project, in manifest order: `{ id, title, year, count, cover, images }`. `id` and `title` are both the client's folder name, as-is, so renaming the folder retitles the project; routes encode it (`encodeURIComponent`) in case a name holds spaces. The manifest carries no dates: a year is read from a filename if one holds a 19xx/20xx, and none do today, so the index shows "—". Real years go in the `YEARS` map, keyed by folder name.

**`src/index-page/index.tsx`** — `IndexPage`: the same projects as a list, on white. **Full-width rows of title + year**, with no header row and no number column. **The gallery's split, carried over** (owner's design, 2026-10-03): the list opens centred in the window (`.inner` is a `min-height: 100%` flex column with `justify-content: center`, padded 5rem top and bottom; past what fits it starts under the frame and the page scrolls). It sat at the bottom of the window for one commit (`23b483d`). **Clicking a row moves the list until that row's line is the centre line, and it stays there.** As a slideshow moves on, **each next row rises onto the line in turn**, like a reel. The list only moves while the hand is still, and the first real movement stops the slideshow, so nothing moves under a moving cursor. **Clicking again (anywhere, even over no row) or the last project ending stops it exactly where it is**: same project and image, the playhead frozen on the spot as a square, no settling (the owner rejected the snap). **While the hand stays still (within `TWITCH_PX`), another click carries on** from that exact point at the same speed (`pausedRef`, `resume`). **A real move, or scrolling, stops it and the row under the cursor takes over**, as the list now sits (scrolling counts as moving: a `scroll` listener on `main`); moving over no row clears the preview (then the random image after 4s). Rows run edge to edge (the page margin is in their padding), so the active line does too. **How the list moves: raising a row is a page scroll; only bringing a row down at the very top is a shift** (`position: relative; top`, never negative). An upward shift drew rows above the page's top edge, where scrolling can't reach (found with `?rows=40`), so scrolling back up couldn't bring the list back; now it always comes back under the nav. Both run in one script animation (`moveList`, rAF) on the row-move curve `cubic-bezier(0.42, 0, 0.58, 1)` (`rowMoveEase`), taking `LIFT_ROW_MS` (500ms) for one row and longer for longer moves, × √rows up to `LIFT_MAX_MS` (1.5s); one fixed 500ms made a ten-row move ten times faster than a reel step. The list's own scrolls are told apart from the user's (`ownScrollRef`), and scrolling up at the top with a shift eats the shift first, so the list goes back to its place. **Room below the list exists only while a raised row needs it** (`.room`, a block after `.inner`, height set from script, `roomFor`): none at rest, so the page ends at the last row (an 11-row list doesn't scroll at all; a long one scrolls exactly to its last row plus margin). Raising a row the page's own end can't reach grows just enough room, and scrolling back up melts it away, never below what the current position needs, so nothing jumps and you can't scroll down into empty space past what a click made. (A fixed half-window spacer was tried for one commit, `bb0bbce`; the owner didn't like the empty space.) The shift is not a transform: a transform would give the list its own stacking context, and the active row could no longer sit over the preview or blend with it. Pointer handling is one window listener (`pointermove`, `click`), and **only real pointer movement or the user's own scroll changes what's hovered**: rows have no hover handlers, because rows sliding under a still cursor (a raise, the reel, the settle) fire mouse events too. An earlier guard that counted moves let the first sliding row through after a move into empty space, so the settle lit a row and hid the random image. Hit-tests use what's really under the cursor at rest and where the list is settling mid-move (`rowAt`). **`/index?rows=40` repeats the projects** to test a long list. **Centred vs. from the top:** the list is centred in the window minus 5rem top and bottom; once it's taller than that it starts at the top margin and scrolls. No visible jump: a list that nearly fills the window is centred with almost no slack, which is the top position. **The index has no scrollbar** (`scrollbar-width: none` plus `::-webkit-scrollbar`); it still scrolls by wheel, trackpad and keys. A stand-in until the gallery-to-index transition exists. **At the same moment the list settles back** (`settleList`) to where the user last left it by scrolling themselves (`userScrollRef`), undoing only what clicks and the reel moved: a short list is centred again, as on landing, and a long one keeps the user's own place; any room below melts with it, on the usual row-move timing. "Off the list" is judged by what's really under the cursor when the list is at rest (`elementFromPoint`), so hovering a nav button over a long list counts as leaving; leaving the browser window does too (`mouseleave` on the document), which also stops a slideshow. **`src/splash/index.tsx`** — `SplashVideo`: the intro video over the canvas. The first wheel captures the current frame, which becomes `SplashPlane` in `scene.tsx`: a plane at cover size that scrolls in depth like the others. **It is seen once**, in two senses. Within a visit, the moment it would wrap round its depth cycle (faded out past the far end, or passed behind the camera) it retires: `onSplashGone` unmounts it and frees the texture, so it can never come back. Across visits, `localStorage["rh:splash-seen"]` is set once the video actually plays, and a returning visitor skips it entirely (so do deep links). To see it again, delete that key. **`index.html` decides whether it plays**, in an inline script before anything paints, and sets `splash` on `<html>`; `App` reads that class (`SKIP_SPLASH`). The page ground (`--color-background` in `src/index.css`) is **white** everywhere, like the canvas and every page, and **black only under the splash** (`:root.splash`), since the video opens on black. It was the Codrops template's black everywhere, which showed for a frame or more on every load before the canvas or a page drew (4 Oct).

### Performance patterns

**`cameraGridRef`**: A `React.RefObject<CameraGridState>` shared with every `MediaPlane`. Updated each frame in `SceneController.useFrame`; planes read `scrollDelta`, `camX`, and `cumulativeScroll` without causing React re-renders.

**Two-stage velocity**: Input accumulates into `targetVel`. Each frame, `velocity` lerps toward `targetVel` (smoothing), then `targetVel` is multiplied by `VELOCITY_DECAY` (friction). Mouse parallax `drift` is separate.

**Depth cycling (scroll zoom effect)**: Scrolling drives `velocity.z` applied to each image's `absoluteZOffset` rather than moving the camera. `effectiveZ = INITIAL_CAMERA_Z - zOffset`. Images right of camera zoom in on scroll-up; left zoom out — direction is re-evaluated against `camX` every frame, so planes flip direction when the camera pans past them. **This camera-relative flip is a non-negotiable design feature** — do not replace it with fixed per-plane directions. Its side effect (two planes can drift to identical depths and then move in lockstep, appearing welded together) is handled by the rest-time depth de-confliction pass in `MediaPlane` (`PlaneRegistry`): while the canvas is at rest, visible pairs closer than 50 depth units and 60 XY units are eased apart at 0.6 units/frame. Opacity fade zones: `depthFadeNear` (fade in), flat visible plateau, `depthFadeStart` → `depthFadeEnd` (fade out + wrap back to 0).

**Depth phase assignment** (`PlaneData.depthPhase`): Pre-computed in `generateChunkPlanes`. All planes in an XY chunk column (3 z-layers × `itemsPerChunk`) are stratified onto evenly spaced depth slots (`zSpread / (3 × itemsPerChunk)` apart — 150 units at defaults). Each column's base phase is `frac(cx·ALPHA_X + cy·ALPHA_Y + sessionFrac)`; the constants are grid-search-optimized so every pair within ±2 columns spawns ≥15.9 depth units apart, with a ±4-window guard against exact rational welds. Beware: constants in an exact rational ratio (e.g. 2:3) lock entire column sublattices to identical phases. Because directions are camera-relative, relative phases drift as the user pans — spawn spacing is a starting condition, and the de-confliction pass handles later convergence.

**XY placement**: Staggered lattice (`utils.ts`) — each chunk's items sit on fixed fractional sites plus a deterministic jitter (radius `JITTER_RADIUS`). For density 2, each of the three z-layers has its own site variant (`LATTICE_VARIANTS_N2`: diagonal / anti-diagonal / center+corner) so no two layers share sites (cross-layer ≥56.6 units pre-jitter). The union across chunks tiles uniformly, capping worst-case empty regions at ~half a chunk while keeping same-layer images ≥83 units apart. Jitter seed includes `SESSION_SEED + cx + cy + cz + item index + cycleNumber` so positions vary per session and per depth cycle.

**Chunk throttling**: Chunk list updates throttle to 100 ms normally, 400–500 ms while zooming fast.

**React Compiler**: `babel-plugin-react-compiler` is active. Do not add manual `useMemo`/`useCallback`.

### Tuning panel

`InfiniteCanvasScene` renders a collapsible tuning panel (visible when `showTuning` prop is true, collapsed by default). Sliders mirror their values into a `tv` React state object (required because React Compiler memoizes direct reads of the stable `tuning` object). Generation-affecting sliders call `bumpGen()` which clears the plane LRU cache and bumps `tuningGenVersion`, causing `SceneController` to immediately remount all chunks.

### Debug system

When `showDebug` is true:
- Bottom-left HUD shows camera pos, chunk coords, vel.z, cumScroll.
- Each `MediaPlane` renders an orange canvas-sprite label showing `cx,cy,cz #index`, visible only when the image is visible.
- Each `Chunk` renders a `ChunkLabel` (blue wireframe + coord sprite) when `showGuides` is also true (toggled via "Show/Hide guides" button in the tuning panel, hidden by default).
